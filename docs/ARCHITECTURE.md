# Архітектура automotive_led_v2

Документ пояснює, **як** влаштована прошивка і **чому** саме так.
Читай зверху вниз: спершу словник, потім загальна картина, потім деталі.

---

## 1. Словник

| Термін | Що означає тут |
|---|---|
| **Подія (Event)** | Маленька структура `{sig, id, tag}`: «що сталося» + «з ким». Єдиний спосіб, яким частини програми повідомляють одна одній новини. |
| **Сигнал (Signal)** | Тип події: `SIG_PIN_EDGE`, `SIG_TIMEOUT`, `SIG_BTN_SHORT/DOUBLE/LONG`. |
| **Черга подій** | FIFO на 16 подій. ISR кладуть туди, головний цикл забирає. |
| **Диспетчер** | Функція `dispatch()` у `main.c`: дивиться на подію і віддає її власнику. |
| **ISR** | Обробник переривання. У нас: `EXTIx_IRQHandler`, `SysTick_Handler`. |
| **Стейт-машина (FSM)** | Змінна-стан (`enum`) + правила «у стані S на вхід X → дія, новий стан S'». |
| **Debounce** | Ігнорування брязкоту контактів: перший фронт → чекаємо 50 мс → читаємо пін один раз. |
| **Жест** | Результат роботи кнопки: SHORT, DOUBLE або LONG. |
| **Програмний таймер** | Лічильник у RAM, який зменшує SysTick раз на 1 мс. Дійшов до 0 → подія `SIG_TIMEOUT`. |
| **Покоління (tag)** | Номер «запуску» таймера. Дозволяє викинути застарілий `SIG_TIMEOUT`. |
| **Config** | `const`-дані, які не змінюються під час роботи (пін, тривалості). Лежать у flash. |
| **State** | Дані, які змінюються під час роботи (поточний стан FSM). Лежать у RAM. |
| **DL / CL / BL** | Driver Layer / Component Layer / Business Layer — три шари, див. розділ 3. |
| **Valet** | Режим «паркувальника»: замок відкритий і заблокований, світиться PC13. |
| **Crash** | Режим аварії після сильного удару: двері відкриті, аварійка, вийти можна тільки у valet. |
| **Composition root** | `main.c` — єдине місце, де всі об'єкти створюються і з'єднуються. |

## 2. Що таке event-driven — на пальцях

Було (стара версія): переривання кнопки **саме** запускало TIM2, а callback таймера **сам**
перемикав реле. Логіка жила в ISR. Додати «довге натискання» чи «подвійне» означало
нагромаджувати `if`-и в обробниках переривань.

Стало: **ніхто нікого не викликає напряму**. Кожен лише каже «сталося X» — кладе подію
в чергу. Головний цикл по черзі роздає події тим, хто за них відповідає.

```
         ПЕРЕРИВАННЯ (швидко, нічого не вирішують)
 ┌────────────────────┐   ┌──────────────────────┐
 │ EXTI: фронт на піні│   │ SysTick: кожну 1 мс  │
 │ → SIG_PIN_EDGE     │   │ → st_tick()          │
 └─────────┬──────────┘   │   → SIG_TIMEOUT      │
           │              └──────────┬───────────┘
           ▼                         ▼
      ┌──────────────── ЧЕРГА ПОДІЙ ────────────────┐
      └──────────────────────┬──────────────────────┘
                             ▼
          ГОЛОВНИЙ ЦИКЛ:  pop → dispatch → (порожньо? → спати)
                             │
      ┌──────────────────────┼─────────────────────────────┐
      ▼                      ▼                             ▼
 SIG_PIN_EDGE           SIG_TIMEOUT                   SIG_BTN_*
 Button (CL)        Button або Led (CL)              Car (BL)
      │                                                  │
      └── кладе SIG_BTN_SHORT/DOUBLE/LONG у чергу ──────►│
                                                         ▼
                                    команди: lock_open(), led_blink(), led_pulse()…
```

Аналогія з Python: це як `asyncio` event loop або `queue.Queue` з одним воркером —
продюсери (ISR) кладуть, один консюмер (головний цикл) обробляє.

### Чому це не полінг (вимога 2)

Полінг — це «постійно питати залізо: а вже натиснули? а вже минуло 500 мс?».
У нас головний цикл **спить** у `__WFI()` (процесор зупиняється) і прокидається
тільки від переривання. Він ніколи не читає кнопку «про всяк випадок».

SysTick раз на 1 мс зменшує лічильники програмних таймерів. Це не полінг
стану системи — це годинник, як метроном. Логіка про нього не знає:
вона просто отримує `SIG_TIMEOUT`, коли треба.

### Чому немає блокуючого коду (вимога 1)

Ніде немає `HAL_Delay()` чи `while (!flag)`. Кожен обробник подій виконується
за мікросекунди й повертається. «Почекати 2 секунди» = «запустити таймер і
повернутися»; через 2 с прийде подія.

## 3. Шари DL → CL → BL (вимога 6)

| Шар | Папки | Знає про | НЕ знає про |
|---|---|---|---|
| **DL** — драйвери | `include/dl`, `src/dl`, `board.c` | регістри, HAL, переривання | кнопки, замки, режими авто |
| **CL** — компоненти | `include/cl`, `src/cl` | DL (піни, таймери, черга) | бізнес-правила, інші компоненти |
| **BL** — бізнес-логіка | `include/bl`, `src/bl` | API компонентів CL | піни, debounce, переривання |
| **App** | `main.c`, `app_config.h` | усіх — з'єднує їх | — |

**Правило залежностей:** шар підключає `#include` тільки шарів **нижче**. Це видно прямо
зі шляху: якщо в `src/cl/*.c` з'явиться `#include "bl/..."` — архітектуру порушено.

**Як компонент передає результат нагору, не знаючи про верхній шар?** Через чергу.
`Button` не викликає `car_on_button()` — він кладе `SIG_BTN_SHORT`. Тому ту саму
`Button` можна взяти в інший проєкт без змін.

`board.c` формально DL, але він знає `ButtonId` — бо це «монтажна схема» саме цієї плати.
Справжні драйвери (`src/dl/*`) id не знають і бачать лише `uint8_t`.

### Файли

| Файл | Що всередині |
|---|---|
| `include/dl/critical.h` | Критична секція (вимкнути/відновити переривання). |
| `include/dl/event.h` | `Signal`, `Event`. |
| `dl/event_queue` | Кільцевий буфер подій, безпечний для ISR. |
| `dl/soft_timer` | 16 програмних таймерів на одному SysTick. |
| `dl/gpio_pin` | `Pin` (порт + пін + активний рівень), маска EXTI на одну лінію. |
| `board.c` / `board.h` | Таблиця пінів і всі ISR. Єдине місце, яке міняєш при перепайці. |
| `cl/button` | Debounce + FSM жестів. |
| `cl/led` | FSM світлодіода: on / off / pulse / blink. |
| `cl/lock` | FSM замка: LOCKED / UNLOCKED. |
| `bl/car` | Режими NORMAL / VALET / CRASH, поворотники, аварійка, гальмо. |
| `app_config.h` | Усі id і всі часові константи. |
| `main.c` | Конфіги, об'єкти, диспетчер, цикл подій. |

Хедери лежать в `include/<шар>/`, сирці — у `src/<шар>/`. PlatformIO додає `include/`
у шлях пошуку, тому підключаємо `#include "cl/button.h"`.

## 4. Відповіді на `question.md`

### 4.1 «Що має йти в структуру даних, а що в конфіг?»

Питання до кожного поля: **«чи може воно змінитися, поки програма працює?»**

- **Ні → конфіг.** Порт і пін кнопки, активний рівень, 2000 мс для довгого натискання,
  номер таймера. Оголошуємо `static const ...` — компілятор кладе це у flash
  (RAM на STM32F411 всього 128 КБ, flash 512 КБ), і випадково змінити `const` не дасть компілятор.
- **Так → стан (state).** Поточний стан FSM, останній стабільний рівень кнопки, режим авто.

Тому кожен компонент має **дві** структури:

```c
typedef struct { const Pin *pin; uint16_t long_ms; ... } ButtonConfig;               /* const, flash */
typedef struct { const ButtonConfig *cfg; ButtonState state; bool pressed; } Button; /* RAM */
```

Стан тримає вказівник на свій конфіг. Аналогія з Python: конфіг — `@dataclass(frozen=True)`,
стан — звичайний об'єкт, який отримав конфіг у конструкторі.

### 4.2 «Окремий таймер на кожну подію чи один на всіх?»

**Один.** Апаратних таймерів мало, і кожен треба налаштовувати. Ми беремо SysTick
(його вже запускає `HAL_Init()` на 1 мс) і робимо на ньому скільки завгодно
**програмних** таймерів — це просто масив лічильників (`dl/soft_timer.c`).
TIM2 зі старої версії більше не потрібен.

Скільки треба зараз: 3 кнопки × 2 (debounce + жест) + 4 LED × 1 = **10** (ліміт 16).
`_Static_assert` у `main.c` не дасть зібрати прошивку, якщо колись перевищиш ліміт.

Точність ±1 мс — для кнопок і поворотників більш ніж достатньо.

## 5. Стейт-машини

### 5.1 Button

**Debounce.** Перший фронт → ISR глушить **свою** лінію EXTI (`EXTI->IMR`) і кладе
`SIG_PIN_EDGE`. Кнопка запускає таймер 50 мс. Коли він сплив: розглушити лінію →
прочитати пін → якщо рівень відрізняється від останнього стабільного, то це
`PRESS` або `RELEASE` для FSM жестів. Брязкіт за ці 50 мс просто не доходить до черги.

**Жести** (та сама таблиця — коментарем у `button.c`):

| Стан | Вхід | Дія → новий стан |
|---|---|---|
| IDLE | PRESS | таймер `long_ms` → PRESSED |
| PRESSED | TIMEOUT | **LONG** → WAIT_RELEASE |
| PRESSED | RELEASE | `double_ms == 0`: **SHORT** → IDLE; інакше таймер `double_ms` → WAIT_SECOND |
| WAIT_SECOND | TIMEOUT | **SHORT** → IDLE |
| WAIT_SECOND | PRESS | стоп таймер → SECOND_PRESS |
| SECOND_PRESS | RELEASE | **DOUBLE** → IDLE |
| WAIT_RELEASE | RELEASE | → IDLE |

Чому подвійне натискання ввімкнене тільки для EMRG: щоб відрізнити SHORT від DOUBLE,
треба почекати 300 мс після відпускання. Для замка це зайва затримка, тому
в його конфігу `double_ms = 0`, і SHORT приходить одразу.

Датчик удару — це теж `Button` (контакт, що замикається): короткий удар = SHORT,
довгий = LONG. Одна реалізація, різні конфіги.

### 5.2 Led

```
OFF ⇄ ON                                     (led_on / led_off)
будь-який → PULSE → (timeout) → OFF          (led_pulse(ms))
будь-який → BLINK_ON ⇄ BLINK_OFF кожні ms    (led_blink(ms), періодичний таймер)
```

Стан і пін змінюються в одній функції `enter()` — неможливо отримати «стан ON, а пін вимкнений».

### 5.3 Lock

`LOCKED ⇄ UNLOCKED`. Найпростіша FSM, але вона все одно окрема: Car не знає,
що реле — це open-drain з активним нулем.

### 5.4 Car (бізнес-логіка)

Стан складається з трьох **незалежних** частин:

- `mode`: `NORMAL / VALET / CRASH`;
- `turn`: `OFF / LEFT / RIGHT` — що вибрав водій;
- `hazard`: аварійка ввімкнена чи ні.

| Режим | Lock SHORT | Lock LONG | EMRG SHORT / DOUBLE / LONG | Crash SHORT | Crash LONG |
|---|---|---|---|---|---|
| NORMAL | відкрити/закрити | → VALET (відкрити) | лівий / правий / аварійка (повтор = вимк) | STOP 1 с | → CRASH |
| VALET | ігнор | → NORMAL | як у NORMAL | як у NORMAL | → CRASH |
| CRASH | ігнор | → VALET, аварійку вимкнути | ігнор | ігнор | ігнор |

Вхід у CRASH: відкрити замок, ввімкнути аварійку.

**Що горить — обчислюється, а не зберігається.** Функція `apply_lights()`:
`лівий блимає = hazard || turn == LEFT`, аналогічно правий. Звідси:

- аварійка має пріоритет над поворотником, але вибір водія не губиться —
  вимкнув аварійку, і поворотник продовжив;
- обидва LED перезапускаються **одним викликом**, тому в аварійці блимають синхронно;
- якщо нічого не змінилося — LED не чіпаємо, щоб не збити фазу блимання.

## 6. Пастки, які обійдено (варто знати)

1. **Конфлікт EXTI0.** Лінія EXTI *x* слухає тільки один порт: PA*x* **або** PB*x*.
   Стара схема мала PA0 (замок) і PB0 (аварійка) — одна з кнопок ніколи б не спрацювала.
   EMRG перенесено на **PB4**. Правило: у кожної кнопки має бути **унікальний номер піна**.
2. **Гонка перед сном.** `if (queue_empty()) __WFI();` — переривання може прийти між
   перевіркою і `WFI`, і ми заснемо з подією в черзі. Рішення в `sleep_until_event()`:
   вимкнути переривання → перевірити → `WFI` (прокидається і з вимкненими) → увімкнути.
3. **Read-modify-write спільного регістра.** `EXTI->IMR |= ...` з головного циклу може
   перерватися ISR іншої кнопки, який теж пише в IMR. Тому — критична секція.
4. **Застарілі таймаути.** Таймер сплив, подія лягла в чергу, а поки вона чекала, ми
   таймер перезапустили. Без захисту подія спрацювала б як нова. Рішення — `tag`
   (покоління): `dispatch()` викидає подію, якщо `st_is_current()` повертає false.
5. **Порядок «розглушити → прочитати».** Якщо прочитати пін до розглушення лінії, зміна
   рівня між цими кроками загубиться. У нашому порядку вона породить новий фронт.
6. **Спільний стан.** З ISR пишуть тільки в чергу (і в лічильники таймерів). Усе інше
   змінює лише головний цикл — один «письменник», гонок немає.

## 7. Припущення (легко змінити)

| Що | Де змінити |
|---|---|
| LED на PA1–PA3 світяться від `1` | `board.c`, `GPIO_PIN_SET` → `GPIO_PIN_RESET` |
| Реле спрацьовує від `0` (open-drain); відпущене = замок закритий | `board.c`, `PIN_RELAY` |
| EMRG і датчик удару замикають на +3.3 В (pull-down) | `board.c`, `active` у `PIN_BTN_*` |
| Вікно подвійного натискання 300 мс, STOP горить 1000 мс | `app_config.h` |
| Вихід з valet залишає замок відкритим | `enter_normal()` у `car.c` |
| Після crash → valet поворотник, вибраний раніше, продовжує блимати | `on_lock()` у `car.c` |
| Одна кнопка EMRG і для поворотників, і для аварійки (кнопок мало) | `on_emrg()` у `car.c` |

## 8. Як додати новий компонент (наприклад, зумер)

1. Пін — у `board.c`/`board.h`.
2. `include/cl/buzzer.h` + `src/cl/buzzer.c`: `BuzzerConfig` (const) + `Buzzer` (state) + FSM.
3. Якщо потрібен таймер — додай блок у `enum` таймерів в `app_config.h` і гілку в `route_timeout()`.
4. Створи об'єкт у `main.c`, передай вказівник у `CarParts`.
5. Керуй ним з `car.c`. DL та інші компоненти не змінюються.

## 9. Перевірка

Перевірено на ПК (без плати): реальний `main.c` + всі модулі зібрано з заглушкою HAL,
яка імітує час, піни з брязкотом 3 мс на кожному фронті та переривання. Результат:

| Сценарій | Очікування | Отримано |
|---|---|---|
| Lock коротко, відпущено @300 мс | реле відкрилось після debounce | 351 мс |
| EMRG коротко, відпущено @1100 | лівий після вікна подвійного (50+300) | 1451 мс |
| EMRG подвійне, відпущено @3230 | правий одразу після debounce | 3281 мс |
| EMRG 2 с від @4000 | аварійка, L і R перемикаються разом | 6051 мс, синхронно |
| Crash коротко | STOP горить 1 с | 10151 → 11151 мс |
| EMRG / Lock коротко під час аварії | ігноруються | ✓ |
| Lock 2 с в аварії | valet, аварійка вимкнена | 21051 мс |
| Переповнення черги | 0 | 0 |

Збірку під саму плату (`pio run`) на цій машині не запускали — PlatformIO тут не встановлено.

### Ручний тест на платі

1. `pio run -t upload`.
2. **Lock коротко** → реле клацає. Швидко «потеребити» кнопку → немає подвійних перемикань.
3. **Lock 2 с** → горить PC13, реле відкрите; коротке натискання нічого не робить. Ще раз 2 с → PC13 гасне.
4. **EMRG коротко** → лівий блимає (≈0,35 с затримки — це вікно подвійного). Ще раз коротко → гасне.
5. **EMRG двічі** → правий. **EMRG 2 с** → обидва синхронно. Ще раз 2 с → назад до правого.
6. **Crash коротко** → STOP на 1 с. **Crash 2 с** → реле відкрите, аварійка; EMRG і Lock коротко не діють.
7. **Lock 2 с** → valet, аварійка вимкнулася.
